OpenClaw Telegram Workflow

Human review for PeopleGraph merges.

This flow lets John's Telegram agent show one proposed identity merge at a time, collect a trusted human approval, and then run the PeopleGraph write command against Botwick's source-of-truth cache.

Inline buttons User ID allowlist Objective fields only JSON audit trail

Why inline buttons instead of polls?

Inline buttons

The button callback carries an exact review ID and action, such as pgm:m_abc123:approve. That maps cleanly to one PeopleGraph command.

Native polls

Telegram polls can work for yes/no review, but the poll answer is a vote rather than an exact command callback. Use polls only as a fallback.

Telegram documents inline keyboards and callback queries in the official Bot API.

Environment

export PEOPLEGRAPH_CACHE="/path/to/botwick/.obsidian/plugins/gmail-crm/contact-index.json"
export TELEGRAM_BOT_TOKEN="123456:telegram-token"
export TELEGRAM_REVIEW_CHAT_ID="123456789"
export PEOPLEGRAPH_APPROVER_TELEGRAM_IDS="111111111,222222222"
export PEOPLEGRAPH_REVIEW_STATE="$HOME/.peoplegraph/merge-review-queue.json"

Queue and send

First import another user's cache with PeopleGraph, then build Telegram review items and send the next pending item to the review chat. 

peoplegraph --cache "$PEOPLEGRAPH_CACHE" import-cache --source kaya /path/to/kaya/contact-index.json

node scripts/peoplegraph-telegram-review.mjs queue --source kaya --limit 25 --min-confidence 0.82
node scripts/peoplegraph-telegram-review.mjs send-next --source kaya

Callback handling

When John's OpenClaw Telegram runtime receives a callback_query, pass the full Telegram update JSON to the bridge script. The script checks the reviewer allowlist, applies or rejects the merge, updates the queue state, and edits the Telegram message. 

node scripts/peoplegraph-telegram-review.mjs handle-callback -

Approve runs apply-external-merge. Reject runs dismiss-external-merge. Details runs contact-card.

Merge policy

Approved merges can add objective identity evidence such as emails, aliases, names, company, role, and future location fields. The shared core record must not absorb private relationship notes, subjective context, email bodies, or source-specific scores.
